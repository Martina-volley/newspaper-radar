01本期焦點

Pin 到一個 commit，不代表實際執行的一定是那個 commit。 AIR Security 指出，部分 agent 外掛安裝器把 Git checkout 成功誤當成完整性驗證，卻沒有在 checkout 後比對實際 HEAD。CSA 於 9/19 發布技術分析，將此歸納為 AI 外掛供應鏈的「請求值與解析結果未核對」問題。

研究方稱 Claude Code 2.1.179 與 Codex 0.146.0 已修正，GitHub Copilot 在披露時未有修補，Gemini CLI 因產品棄用不修補；但本期未找到四家供應商一致、可交叉核對的正式安全公告，因此版本狀態仍應由企業自行向供應商確認。

03為什麼重要

  • 供應鏈控制可能只驗了名稱：marketplace 記住核准的 SHA，但 client 沒驗證最後落地的內容。
  • 自動更新放大影響：若更新無需互動，已安裝的可信外掛可在上游遭控制後被換成惡意內容。
  • Agent 權限就是外掛權限：外掛若在開發者工作站上執行，可能接觸原始碼、雲端憑證與內網服務。
  • 目前仍不是已知遭利用：公開資料支持可行攻擊鏈，不支持「已造成大規模受害」的說法。

04Agent 行為痕跡

安裝與更新

預期 SHA 與 git rev-parse HEAD 不一致；checkout 出現 ambiguous ref 警告；外掛來源的 default branch 突然變更。

執行與權限

更新後立即出現新子程序、讀取 SSH／雲端憑證、掃描 workspace、連往新網域或嘗試存取內網服務。

證據完整性

marketplace 顯示的 pin、local lockfile、實際 Git object 與執行檔雜湊不一致；Agent transcript 未記錄背景更新。

05對企業的影響

  • 先盤點 Claude Code、Codex、Copilot、Gemini CLI 的外掛／plugin／skill 來源與自動更新狀態。
  • 外掛升級要比對 resolved commit、內容雜湊與簽章，不只比對 marketplace 顯示值。
  • coding agent 應以獨立短效身分執行，不沿用開發者的長效雲端憑證。
  • 無法確認修補狀態的產品，先停用第三方外掛自動更新，或移到隔離 runner。

06我們應追蹤什麼

073 句結論

  1. 本期沒有官方確認的重大新 AI 資安事件，應把資源放在驗證既有控制，而不是放大未確認說法。
  2. Plugin4Shell 的核心教訓是「核准的識別碼」不等於「實際執行的內容」；安裝後必須驗證 resolved state。
  3. 短期最有效措施是更新工具、停用無法驗證的自動外掛更新，並讓 agent 在低權限、受限出口的隔離環境中執行。
